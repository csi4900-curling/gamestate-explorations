# Postscore left-view path-censoring diagnostic

This is an **exploratory development audit**, not part of the frozen full-match screen or an independent recall estimate. Full-match hold samples show 1443 of 1444 left-view frames directly registered, but only 32 of 60 left-view candidates retained a unique path. Thus camera registration alone cannot explain left-view path loss. Source inspection of S125, S127, S133 and S137 shows a moving stone in the left view around or after the end of the fixed 12 s candidate window. These four cases were selected after seeing the screen failures and must not be used as a validation sample.

Run the unchanged high-resolution proposal detector on each of the four candidate windows with **20 s lookahead** and the same 0.5 s sampling, source file, 6525 s right anchor, calibration, and 160 px registration gate. First compare the frozen path selector unchanged (`min_forward_step_m=0.3`, `min_travel_m=2.0`). Then, on the stored 20 s proposals only, perform a clearly labeled parameter sensitivity audit for left-view `min_forward_step_m` values 0.3, 0.2, 0.15 m per sample while keeping `min_travel_m=2.0` and all other rules unchanged. Report path counts, ambiguity, and first/last observed times. Do not promote any recovered path to a confirmed throw or revise the frozen screen based on these cases.

The point is to distinguish a **window-censoring** failure from a **slow-motion threshold** failure before committing a new rule for all views and recordings. A candidate-wide, predeclared transfer with independent labels would still be required to establish a recall improvement without a precision cost.
