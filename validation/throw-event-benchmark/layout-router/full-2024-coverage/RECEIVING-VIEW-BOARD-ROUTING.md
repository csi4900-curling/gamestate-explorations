# Post-candidate board sampling must follow the receiving view

The previous split-screen full-match state handoffs sampled post-candidate cap sets in the **right panel for every left-panel passage**. The S38 [source review](../../canada-estonia-2024/S38-HIGHRES-STATE-ENRICHMENT.md) shows why that can inspect the wrong end: a right-panel stone moving toward the camera precedes a left-panel passage, after which the left panel shows the receiving house.

The [conditional router](../../../../prototype/split_board_view_routing.py) uses the direction and order of each unique right/left candidate link. Right `positive_y` motion **before** a left passage routes the post-candidate view to **left**; right `negative_y` motion **after** it routes to **right**. Missing, competing, or conflicting links abstain. These routes are hypotheses about the two-panel layout, not verified physical throw identities.

For the left-routed candidates, a [new 360p colour-cap sampler](../../../../prototype/scripts/scan_routed_left_post_caps.py) takes frames at passage +25, +30 and +35 s only when all precede the next full-match candidate by at least 1 s. It finds repeated left-panel colour blobs in **57/62** Estonia routes and **34/43** Italy routes; it abstains in four and nine short windows, respectively. The other Estonia route has no repeated blob. These are image proposals, not identified stones or measured boards. In S38, the 360p yellow centres (84,192) and (236,259) agree with the 1080p source observations after 3× scaling. The same S38 scan also repeats a red blob from the lower-left rink marking, demonstrating that stability alone is insufficient to classify stones.

The [Estonia](../../canada-estonia-2024/full-match-conditional-receiving-view-state-handoff-postreview.json) and [Italy](../../canada-italy/full-match-conditional-receiving-view-state-handoff-transfer.json) full-match handoffs now attach a `post_candidate_receiving_view_observation` to each routed candidate. Left routes use the new left scan, right routes preserve the existing right scan, and abstentions leave that field null. Every added observation has `complete_board_verified: false`, `physical_settle_verified: false`, and `simulation_ready: false`; the original `game_state_after` remains unknown. Right-only candidates remain separate rows.

The next development pass also samples the left receiving view at passage −35, −30 and −25 s, subject to a 1 s guard after the previous candidate. It compares the bounded pre/post image-cap sets only when a top-ice scene patch changes by less than 10 mean pixel levels. The [Estonia transition handoff](../../canada-estonia-2024/full-match-conditional-receiving-view-state-transitions-postreview.json) contains **57** left-view image comparisons and **five** window abstentions. The [Italy transfer](../../canada-italy/full-match-conditional-receiving-view-state-transitions-transfer.json) contains **29** comparisons, ten window abstentions and four scene-change abstentions. Right-routed rows retain the previous right-view transitions; unrouted rows stay unknown.

For S38, the [pre/post delta](../../canada-estonia-2024/full-match-routed-left-pre-post-cap-deltas-postreview.json) retains the static red rink marking and one yellow cap at the same image positions. A yellow pre-cap near (92,219) is no longer observed and a yellow post-cap near (236,259) is newly observed. The local IDs in the pre and post sets are separate; this does **not** prove where the delivered stone stopped or which stone moved. It does show why a same-view before/after comparison is more informative than treating every persistent colour blob as a newly thrown stone.

An [event-filter diagnostic](routed-cap-delta-event-filter-diagnostic-postreview.json) checked whether these changes could discriminate false throw proposals in the two saved 1650–2760 s coarse-reference intervals. The later full-match sequences already place exactly 17 left candidates inside 17 frozen windows for **each** recording, with no unmatched candidate in either interval. Thus these data provide **no negative candidate denominator** for testing cap-delta false-positive rejection. The apparent 17/17 agreement is an exposed development-sequence property, not a new detector validation result. We do not add a cap-delta throw acceptance rule from it.

A follow-up [high-recall proposal diagnostic](CORRIDOR-CLUSTER-BOARD-FILTER-DIAGNOSTIC.md) uses the earlier corridor lists with 12 unmatched candidates across Estonia and Italy. Bounded cap comparison abstains on all extras and several matched windows; grouping close same-colour/direction passages improves the exposed coarse count but still leaves unmatched groups. Neither observation supports a hard board-change throw filter.

This is an exposed two-recording development replay. The router has no independent cross-camera identity labels, the cap sampler has no stone-versus-person validation, the top-ice MAE guard does not calibrate the camera, and unseen throws can occur between the sampled windows. It improves which images and changes are represented in the candidate state sequence; it does **not** improve measured event precision/recall/F1 or yield simulation-ready game states.

Reproduce from the saved sequences with `route_full_match_split_board_views.py`, `scan_routed_left_post_caps.py`, `scan_routed_left_pre_caps.py`, `compare_routed_left_pre_post_caps.py`, `attach_full_match_routed_partial_caps.py`, then `attach_full_match_routed_left_deltas.py`; each command accepts source/sequence/route paths and writes input hashes.
