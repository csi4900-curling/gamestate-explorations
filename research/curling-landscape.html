A field guide to the software, formats and datasets that can turn curling footage into useful game state—and the parts we still need to build.

The recommendation

Reuse the curling knowledge. Add a thin layer for what the camera actually knows. Treat a Rust port as a focused engineering choice, with correctness demonstrated against a pinned reference.

01

First, separate the four problems.

“A representation of curling” can mean several different things. No single project below solves all of them. This distinction helps us reuse the right components.

01 / SeePerceptionFind stones and rink markings in pixels.
02 / DescribeRepresentationRecord positions, teams, shots and uncertainty.
03 / PredictSimulationEstimate where stones go after a delivery.
04 / DecideStrategyCompare possible shots and expected outcomes.

Our immediate task is the bridge from See → Describe. A simulator becomes useful once the board is trustworthy. It cannot recover a hidden stone merely because the state format has a slot for one.

Terminology: the house is the scoring target; the tee/button is its centre; an end is a round of deliveries; the hammer is the last-stone advantage. Mixed doubles starts with two pre-positioned stones, so a board can exist before the first delivery.

02

The landscape worth knowing.

Three especially useful starting points: DC4 for simulation-compatible state, PCN for portable match records, and Curlovision for an existing video-to-layout pipeline.

Core interoperability target

Digital Curling 4

A match server and typed state model for standard curling and mixed doubles. It supplies the vocabulary for teams, scores, end/shot counters, stone coordinates and setup choices.

Its Python service calls a separate native physics module. The DC4 Python client is a useful reference for consuming its state.

Use it for: a pinned export contract and rules reference. It does not represent per-stone occlusion, video evidence or positional uncertainty.

Promising · unofficial draft

Portable Curling Notation

PCN is a text format, with a JSON schema, for recording a match one shot at a time. It can carry scores, shot descriptions, settled stone positions and engine-specific release parameters.

It has tee-centred metre coordinates and mixed-doubles setup examples. It is a recent draft, not a World Curling standard or a proven ecosystem.

Use it for: an exchange/export format for reconciled records. Its complete board lines should not silently stand in for a partially visible frame.

Closest video precedent

Curlovision

An existing pipeline that finds house rings and stones, reads scoreboards, and groups layouts into ends and matches. Its object hierarchy is already close to the architecture we discussed.

The code targets older Python and particular broadcast layouts. It is a baseline to study and modernise; its reported performance has not been reproduced here.

Use it for: pipeline ideas and a comparison baseline. The broad video-to-game-state idea already has prior art.

Reference data

CurlR

Shot metadata and stone layouts extracted from official results-book diagrams. Our feasibility experiment already uses it to compare calibrated video positions against reference layouts.

Its wide tables and diagram coordinates are useful import data. They are not a general uncertainty-aware state model, and the diagrams are not surveyed physical ground truth.

Use it for: reference matching and historical shot metadata, with diagram provenance retained.

Official metadata

Olympic Data Feed & SportsML

The Olympic curling dictionary defines structured match and shot events. Its play-by-play board is supplied as image data, rather than a metric stone-position array. IPTC SportsML defines curling statistics and event vocabulary.

Use them for: established names and semantics. Neither inspected specification replaces our video calibration and observation layer.

Physics & perception building blocks

FCV1, DC3 & CurlObserver

FCV1 is the C++/Box2D physics module used by DC4, exposed through Python bindings. DC3 is an earlier C++ platform with JSON state and tests. CurlObserver supplies detection, segmentation and tracking labels.

Use them for: simulation and perception work respectively. Tracking IDs and image boxes alone do not tell us the end, hammer or complete game state.

A correction to the initial recommendation: PCN deserves evaluation alongside DC4. DC4 remains the simulation target; PCN may be a better human-readable match archive. Our observation layer can feed both without making either format responsible for raw camera uncertainty.
03

A small addition, with a big job.

Keep observations separate from reconciled game state. Multiple camera views may describe the same board. A cropped view may describe only part of it.

Interactive example

Is that the whole board?

The camera shows two stones. A guard could be outside the frame. Record a partial observation; do not export this as a confirmed two-stone board.

An absent detection is evidence about the image—not proof that a stone is out of play.

What belongs in our observation layer?

Frame-local observation IDs; team/colour where known; position and coordinate convention; visibility and completeness; observed versus inferred status; calibration/evidence references; uncertainty with its estimation method. Leave unknown identity and unmeasured uncertainty unknown. A detector confidence is not automatically a position-error estimate.

What compatibility traps should we handle explicitly?

DC4’s tee is at y = 38.405 m; PCN uses the tee as the origin with positive y toward the thrower. With matching x orientation, yDC4 = 38.405 − yPCN. DC4 uses (0, 0) for unused/absent slots, not for the button. Team identity must remain separate from colour and throwing order. Pin historical rules for 2018 footage; the inspected DC4 placement tables include 2026–27 changes. See the rules implementation.

Does the playbook’s GAMESTATE definition still apply?

Treat the old literal GAMESTATE example as a legacy model. Current DC3 and DC4 use different fields and conventions. Adopt an explicit, versioned adapter rather than copying the old structure and calling it universally compatible.

05

Should we port it to Rust?

A small, tested Rust core could be a good idea. AI-assisted translation looks tractable for the data model and pure rules. I would not call a verified replacement for the whole platform trivial.

The detail that changes the decision

The physics is already native code.

DC4’s Python simulation service calls StoneSimulator. FCV1 implements the dynamics in C++ with Box2D and pybind11. Porting the HTTP server to Rust does not, by itself, replace or accelerate that physics loop. Performance gains need a measured bottleneck.

Where agentic AI helps—and what still needs proof.

Translation is tractable

Agents can translate types and functions, write adapters, build fixtures, and run comparisons. A narrow state-and-rules port is a sensible task.

Behaviour is the contract

Matching field names is insufficient. Preserve absent-stone semantics, team mapping, clock/end transitions, spin signs, numeric precision and historical rules.

Verification is the deliverable

Compare both implementations on the same inputs. Add independent rule cases so shared bugs do not count as success. For physics, compare trajectories and collisions within declared tolerances.

My judgement: your optimism is reasonable about generating a first port. The uncertainty is the effort required to establish equivalence and maintain it. We should make that effort visible through acceptance tests, rather than equating compiling Rust with a robust replacement. No Rust port or speed benchmark was performed for this report.

06

A concrete path forward.

Build one trustworthy slice from our existing evidence to an interoperable record. Keep a potential Rust implementation small enough to verify.

Freeze the contract

Define board observations, reconciled snapshots, units, axes and unknown values. Pin DC4 and the PCN draft. Keep raw observations even when export is not yet possible.

Use the pilot as fixtures

Convert existing annotations; render the same board; test coordinate round-trips, colours and stone counts. Include a crop, an occlusion and the mixed-doubles initial setup.

Prove interoperability

Export a sufficiently known snapshot to DC4 conventions and a settled record to PCN. Preserve missing context instead of inventing clocks, stone identity or unseen positions.

Then choose the implementation

If Rust is preferred, implement the state/adapters and pure rules against the fixtures. Expand to another broadcast before expanding the service or rewriting physics.

Acceptance gate: partial views remain partial; round-trips preserve positions within an explicit tolerance; rule fixtures agree with the reference and independent expectations; a second match exposes no silent camera- or scoreboard-specific assumptions.

What was—and was not—tested?

Ran three upstream test modules: test_match_rules.py, test_scoring_rules.py and test_simulation.py. All 18 tests passed in an isolated environment. Other code was inspected, not comprehensively executed. We did not run the complete DC4 application, compare physical trajectories against measured ice data, benchmark a Rust port, or reproduce Curlovision accuracy. An upstream README still says “Add tests”; actual test files take precedence over that stale checklist item.
